01 Назначение и приоритет

HOML — текстовый формат для двух задач одновременно. Они тянут дизайн в разные стороны, поэтому приоритет задан явно.

Главное

Конфигурация, которую пишет и читает человек

Отсюда вытекают комментарии, многострочные строки, маркер ? и требование к качеству сообщений об ошибках. Самодокументируемость важнее минимализма: config.example.homl должен заменять раздел README со списком полей.

Вторично

Формат данных, возвращаемых сервисом

Отсюда — массивы объектов, анонимный корень, устойчивость к недоверенному вводу и лимит глубины. Производительность в v1 не оптимизируется, но архитектура не должна её закрывать.

При конфликте двух задач выигрывает первая. Пример действующего решения: маркер ? оставлен в языке, хотя в wire-формате он бесполезен и дублируется на каждом элементе массива.

02 Правила языка

Это вход для docs/SPEC.md, а не замена ему. Спеку писать вам — в том числе потому, что EBNF-грамматика есть проверка: правило, которое не записывается без оговорки «а тут зависит от…», означает неустранённую неоднозначность.

Решено ваше решение, зафиксировано
Допущение моя рекомендация, можно переопределить
Решено

Поле — ключ: значение, разделителей между полями нет

Ни запятых, ни точек с запятой. Ключи без кавычек.

Решено

Голые слова как значения запрещены

Кавычки у строк обязательны. Именно этот запрет и позволяет жить без разделителей: IDENT в позиции значения однозначно означает, что значения не было, — хватает одного токена lookahead.

tags: ["network", "auth", "db"]   // так
tags: [network, auth, db]         // ошибка
Решено

Блок — имя { … }, вложенность любая, inline разрешён

tdlib { version: "1.8.0" }
Решено

Типы: строка, многострочная строка, число, true/false/null, массив

Многострочные — в обратных кавычках. Массивы [a, b, c] допускают смешанные типы.

Решено

Комментарии // и блочные

Лексер обязан разбирать строковые литералы раньше, чем искать //, иначе любой URL внутри строки развалит файл. Это первый тест лексера.

origins: ["http://myapp.com"]  // не комментарий внутри строки
Решено

Маркер ? — часть объявления поля, не значения

Означает: поле можно не указывать, пустота здесь ожидаема. В AST — флаг у поля; парсер его только сохраняет, читают форматтер и будущий валидатор.

Решено

Пропущенное значение → null, и только при ?

Для поля без ? отсутствие значения — ошибка. Это единственное, что защищает от «забыл дописать значение»: пустота легальна лишь там, где автор сам заявил ?.

middle_name?:          // null
host:                 // ошибка: ожидалось значение
Решено

Значение начинается на строке своего :

Проверяется сравнением номеров строк у токенов — отдельного токена перевода строки в потоке нет. Правило действует для всех полей, однородно. [, { и открывающая обратная кавычка остаются на строке ключа, их содержимое многострочное.

Допущение

Объект — полноценное значение

То есть key: { … } легален, имя { … } — синтаксический сахар над ним (один и тот же узел AST), корень документа — неявный объект. Без этого решения users: [{…}] и анонимный корень { status: 200 } вне грамматики, а значит формат не выражает ответ сервиса.

Если переопределите — HOML становится языком конфигов и только; массивы объектов и анонимный корень выпадают, второй сценарий из §1 закрывается.

Побочное следствие принятого варианта: набор видов значений совпадает с JSON — скаляры, массив, объект, — поэтому печать дерева в JSON тотальна по данным (теряются комментарии и маркер ?). Синтаксического включения при этом нет ни в одну сторону: JSON-файл не разбирается как HOML из-за кавычек у ключей, запятых между членами и запрета точки в ключе. HOML — самостоятельный формат, а не JSON с сахаром.

Допущение

Ключ: [A-Za-z_][A-Za-z0-9_-]*

Точка запрещена — иначе путь в API (server.tls.enabled) становится неоднозначным. Ключ, совпадающий с литералом (true, null), парсер принимает: лексер выдаст токен литерала, и это надо предусмотреть заранее.

Допущение

Числа: int64 и double хранятся раздельно

Единый double молча потеряет точность на 17-значных идентификаторах из ответов сервиса. Формы: целое со знаком, дробное, экспонента. 0x, 1_000, +1, .5 — не входят в v1.

Допущение

Многострочные строки: отступ срезается по закрывающей кавычке

Первый перевод строки после открывающей кавычки отбрасывается; отступ закрывающей задаёт базовый и вычитается из всех строк. Так делают C# 11 и Swift. Без этого правила значение зависит от красоты отступов в файле.

banner: `
    Welcome
      to HOML
`   // → "Welcome\n  to HOML"
Допущение

Прочие умолчания

Запятая в массиве обязательна, висячая разрешена. Блочные комментарии вложенные (счётчик глубины; незакрытый указывает на своё начало, не на EOF). Дубликат ключа в одном объекте — ошибка, не перезапись. Порядок ключей сохраняется. \r\n нормализуется в \n при чтении. Файл — UTF-8, BOM допускается и отбрасывается. { блока разрешён на следующей строке.

03 Открытые вопросы

Закрыть до начала работы над лексером: каждый из них меняет либо набор токенов, либо форму AST.

ВопросВариантыРекомендация
Набор escape-последовательностей в "…" \n \t \" \\ \uXXXX Этот набор, без \xNN. Сырой перевод строки внутри "…" — ошибка, и лексер обязан оборвать её на конце строки, а не глотать файл до конца
Обратные кавычки — raw или с escape raw / с escape raw: внутри нет ничего, кроме текста. Цена — обратную кавычку внутрь вставить нечем; если нужна, потребуется ограничитель вида ```
? на блоках: tls? { … } да / нет Да, иначе блоки неравноправны значениям. В массивах ? запретить явно
Лексема маркера часть IDENT / отдельный токен Отдельный токен ?, смежность с ключом проверяется по позициям. Иначе валидным станет либо a?b?c, либо secret ? : 1
Два поля в одной строке разрешено / одно поле на строку Разрешить: запрет ничего не защищает. Форматтер при выводе раскладывает по строкам
Канонический вывод пустого поля key?: / key?: null Писать null явно. Пустая форма — удобство ввода, вывод однозначен
Различимы ли «поля нет» и «поле = null» в API да / нет Для отчества — нет, для retries?: null («явно отключено») может быть да. Решение влияет на сигнатуру доступа, принять до §4

04 Архитектура

Пять слоёв с односторонней зависимостью: каждый знает только о предыдущем. Это условие того, что лексер можно тестировать без парсера, а парсер переписать без переписывания API.

Source
Буфер файла, имя для диагностики, нормализация \r\n, отбрасывание BOM. Владеет текстом и живёт дольше всего, что на него ссылается.
Lexer
Поток токенов с позицией. Пробелы, переводы строк и комментарии пропускаются молча — токена перевода строки нет. О грамматике не знает ничего.
Parser
Рекурсивный спуск, LL(1): после IDENT один токен lookahead решает, поле это или блок. Ошибку не выбрасывает — записывает в диагностику и восстанавливается.
Value / AST
Дерево. Скаляры, массив, объект, флаг optional у поля, позиция узла для сообщений уровня валидации. Решите, кто владеет строками: ссылки в буфер быстрее, но связывают время жизни дерева с источником.
API
Типизированный доступ по пути (server.tls.enabled), обход, запрос с умолчанием. Поверх — форматтер, печатающий дерево обратно в канонический HOML.

Инварианты, которые нельзя нарушать

  • Диагностика — список, а не исключение: за один проход собираются все ошибки файла.
  • Восстановление после ошибки: пропускать токены до первого, у которого номер строки больше текущей и за которым идёт : или {, — это начало следующего поля.
  • Позиция хранится как смещение; line:col вычисляется лениво. Так дешевле и так проще будет перейти на UTF-16-колонки, если однажды появится LSP.
  • Лимит глубины вложенности обязателен с первого дня: рекурсивный спуск на файле из десяти тысяч [ роняет процесс, а разбор данных из сети — недоверенный ввод.

Грабля, которую вы встретите в первый же час. Рекурсивный тип значения нельзя объявить напрямую: на момент объявления он неполон. Контейнер последовательности с неполным типом стандарт допускает, ассоциативный — нет. Решений несколько, и выбор определяет, останется ли значение копируемым и сколько аллокаций приходится на узел. Решите это осознанно, а не первым найденным способом.

05 Структура репозитория

Текущее состояние — шаблон CLion: пустой main.cpp, шесть строк CMake, никакого git. Целевое — библиотека, тонкий CLI поверх неё и тесты, которые линкуются к библиотеке, а не к исполняемому файлу.

ПутьСодержимое
include/homl/Публичные заголовки: значение, документ, диагностика, точки входа разбора и печати
src/Реализация: source, lexer, parser, value, diagnostics, formatter
tests/Юнит-тесты лексера и парсера + прогон корпуса
tests/corpus/valid/*.homl + ожидаемый канонический дамп дерева
tests/corpus/invalid/*.homl + ожидаемый текст ошибки с позицией
examples/config.example.homl, response.example.homl — те самые два сценария из §1
docs/SPEC.mdСпецификация и EBNF-грамматика
tools/CLI: проверка файла и форматирование

Что исправить в CMake сразу

  • cmake_minimum_required(VERSION 4.3) — версия, которую подставил CLion. Для библиотеки нужен диапазон вида 3.20…4.4, иначе сборка недоступна всем, у кого CMake старше.
  • Стандарт задан глобальной переменной без требования обязательности — компилятор молча откатится на доступный. И без отключения расширений вы собираете gnu++23, а узнаёте об этом на чужой машине. Стандарт и предупреждения задаются на цели, а не глобально.
  • Предупреждения: как минимум полный набор плюс диагностика сужающих преобразований — для лексера это рабочий инструмент, а не формальность.
  • Санитайзеры адресов и неопределённого поведения в отладочной сборке. Для разбора текста это основной способ отладки.
  • enable_testing() и CTest. Тестовый фреймворк — doctest или Catch2 через FetchContent; GTest для этой задачи тяжеловат.

06 Этапы работ

Порядок существенный: каждый следующий этап опирается на критерий готовности предыдущего. Нумерация — последовательность, а не список.

  1. 00

    git

    До единой строки кода. Проект уже был утрачен целиком: истории не было, корзина пуста, файловая система без снапшотов, локальная история IDE содержит только шаблон. Второй раз эта цена не нужна.

    Готово, когда есть первый коммит, .gitignore закрывает каталоги сборки и настройки IDE, и настроен внешний remote.
  2. 01

    Спецификация и грамматика

    docs/SPEC.md: решения из §2, ответы на §3, EBNF. Грамматика здесь — инструмент проверки, а не украшение: место, которое не записывается формально, и есть неоднозначность, за которую вы заплатите в парсере.

    Готово, когда каждое правило записано без оговорок «зависит от контекста», а все семь вопросов §3 закрыты.
  3. 02

    Корпус тестов

    Исполняемая часть спеки, и она пишется раньше кода. Каждый спорный случай из §2 и §3 становится файлом: валидным с ожидаемым деревом или невалидным с ожидаемым текстом ошибки.

    Готово, когда оба примера-сценария и все пограничные случаи лежат в корпусе, а запуск тестов падает по существу, а не из-за отсутствия кода.
  4. 03

    Каркас сборки

    Библиотека, CLI, тесты; предупреждения, санитайзеры, CTest — по §5.

    Готово, когда cmake --build и ctest проходят на пустой реализации, а отладочная сборка включает санитайзеры.
  5. 04

    Лексер

    Токены с позициями. Собственные тесты: URL внутри строки, незакрытая строка, незакрытый блочный комментарий, вложенные комментарии, обратные кавычки с отступами, числовые формы, ключ-литерал.

    Готово, когда на каждый файл корпуса выдаётся ожидаемый поток токенов, а каждая лексическая ошибка имеет точную позицию начала.
  6. 05

    Парсер и дерево

    Рекурсивный спуск по грамматике из этапа 01. Сюда же — правило строки значения, подстановка null при ?, лимит глубины, проверка дубликатов ключей.

    Готово, когда весь валидный корпус даёт ожидаемые деревья, а невалидный — ошибки в ожидаемых позициях.
  7. 06

    Диагностика

    Несколько ошибок за проход, восстановление, подсказки по §7. Выделено в отдельный этап намеренно: именно здесь парсер становится пригодным для людей.

    Готово, когда файл с тремя независимыми ошибками выдаёт три сообщения за один запуск, а тесты сверяют их текст, а не только факт.
  8. 07

    Публичное API

    Доступ по пути, типизированное чтение, умолчания, обход. Решение из последней строки §3 здесь становится сигнатурой.

    Готово, когда оба примера из examples/ читаются прикладным кодом без знания о внутренних типах парсера.
  9. 08

    Форматтер

    Печать дерева в канонический HOML: один стиль отступов, явный null, сохранённый порядок ключей.

    Готово, когда повторное форматирование не меняет результат и разбор напечатанного даёт исходное дерево.
  10. 09

    Схема и валидатор

    Отдельный документ, описывающий форму: обязательность, типы, диапазоны. Здесь ? наконец начинает что-то проверять. За пределами v1, но архитектура не должна этому мешать — поэтому флаг optional в дереве сохраняется с этапа 05.

    Готово, когда решено, отдельный это файл или аннотации в данных.

07 Диагностика

Требование, а не пожелание: хороший парсер отличается от плохого именно сообщениями. Большинство хороших сообщений получаются не из грамматики, а из контекста, который парсер и так держит в руках.

Обязательный минимум сообщения

  • Файл, строка, колонка — указывают на причину, а не на место, где парсер споткнулся.
  • Фрагмент источника с указателем на проблемный токен.
  • Подсказка с готовым выходом, а не только констатация.

Эталонный случай

Отъехавшее значение парсер обнаружит и без специальной проверки: null подставлен, дальше в позиции ключа оказывается строка. Но сообщение по умолчанию укажет на строку 8 и скажет «ожидался ключ» — человек будет искать проблему в кавычках. Решается одним флагом состояния: парсер помнит, что предыдущее поле получило неявный null, и если следующим приходит токен, который мог бы быть значением, выдаёт точное сообщение.

error: значение поля 'secret' должно быть на строке 7, рядом с ':'
  7 |     secret?:
  8 |     "abc123"
      |     ^ эта строка не может быть ключом
hint: перенесите значение на строку 7 либо удалите её —
      поле останется пустым (null)

08 Тесты и устойчивость

Уровни

  • Юнит-тесты лексера — поток токенов и позиции на пограничных входах.
  • Корпус — валидные файлы против ожидаемого дампа дерева, невалидные против ожидаемого текста ошибки. Сверять текст, а не только факт ошибки: иначе качество сообщений деградирует незаметно.
  • Round-trip — печать и повторный разбор дают исходное дерево; повторное форматирование ничего не меняет.
  • Дифференциальный оракул через JSON — печать разобранного дерева в JSON и сверка с доверенным JSON-парсером. Направление только HOML → JSON, и работает оно потому, что наборы видов значений совпадают, а не из-за родства синтаксисов. Обратно JSON-корпус механически не переписывается: кавычки у ключей, запятые между членами, запрет точки в ключе, другой набор escape-последовательностей. Как источник стресс-кейсов — глубина, числовые края, юникод — он годится, но только через написанный трансформер с отображением невыразимых ключей. Бесплатных тысяч кейсов нет: корпус из этапа 02 пишется руками.
  • Фаззинг — хотя бы несколько минут на случайных и мутированных входах. Цель не «разобрал правильно», а «не упал и не ушёл в бесконечность».

Устойчивость

  • Отладочная сборка под санитайзерами проходит весь корпус чисто.
  • Глубина вложенности ограничена; превышение — обычная ошибка разбора, а не падение.
  • Обрезанный файл, одиночная кавычка, незакрытая скобка, нулевой байт, неполная UTF-8-последовательность — диагностика, а не неопределённое поведение.

09 Приёмка v1

Проверяется по этому списку целиком. Пункт, который невозможно отметить, — это либо незакрытый вопрос из §3, либо пропущенный критерий готовности из §6.

  • Оба сценария из §1 выражаются в HOML и разбираются: конфиг с вложенными блоками и ответ сервиса с массивом объектов.
  • Все семь вопросов §3 закрыты в docs/SPEC.md, грамматика записана формально.
  • Поле без ? и без значения даёт ошибку; с ? — null.
  • Значение, отъехавшее на другую строку, даёт сообщение с указанием на строку ключа и подсказкой.
  • Файл с несколькими независимыми ошибками выдаёт их все за один запуск.
  • Каждая ошибка корпуса совпадает с ожидаемым текстом и позицией.
  • Round-trip устойчив; повторное форматирование — тождество.
  • Корпус проходит под санитайзерами без замечаний.
  • Фаззинг не находит падений и зависаний.
  • Прикладной код читает оба примера через публичное API, не зная о внутренних типах.
  • Сборка проходит на чистой машине без CLion: только CMake, компилятор и CTest.
